这次重构的终极目标是：优化userSession，让它更易于阅读、理解。

userSession在这里的作用是：已登录用户的总控制器。为了体现它目前的地位，可以在controller包下面，单独创建一个usersession文件夹，
里面提供一个主入口，然后按照用户类型的不同，把控制器拆分成管理员和普通用户各自的总控制器。然后应用策略模式、工厂模式和命令模式的结合，
对这个超级控制器进行改造。

为了避免重构时，状态管理与业务逻辑耦合在一起，事实上的第一步是剥离出状态机。
这是程序的所有状态信息：

public enum Authenticated {
	/**
	 * 用户未登录，可以自主选择注册为新用户，或者以老用户身份登录。
	 */
	NOT_AUTHENTICATED,
	
	/**
	 * 用户已登录，应该进入已登录用户的会话页面。
	 */
	AUTHENTICATED
}

只要状态改变的请求不符合这个流程，就一律阻止。

为了保证安全性，状态机应该是无状态的。

状态改变的流程：
首先检查当前状态，然后预测下一个可行的状态改变。如果下一个状态的改变在范围之内，检查通过。如果引入令牌技术，会加入用户状态的检查。

状态分为两种：未认证和已认证。
未认证对应以下动作：尝试登录、尝试注册。
登录失败
尝试登录成功后，状态变为已认证。如果登录失败，状态保持不变。
状态处于已认证时，对应用户退出这一行为。

将使用Map对状态、动作进行关联。Key是状态，Value是动作。

服务层向状态机发起操作请求。状态机接收到请求后，根据内部规则，决定是否批准，告诉服务层结果。
服务层根据状态机的响应，自己处理数据，处理成功/失败后，告诉状态机结果，状态机自行改变状态；然后服务层把结果返回给控制器，控制器完成剩下的流程。
这样，状态机就能巧妙的执行动作->改变状态，但是又不必亲自操作控制器，反而是与控制器借由状态机自身的实例来通讯。由于状态机无状态，可以减少安全风险。
