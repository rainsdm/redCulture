我改变了用户的id规则，并且加入了账户创建时间与上一次访问的时间。经过代码检查，已确认不需要我做大幅重构，UserDao没有问题。
只需要小幅修改user模型，让它能够存储上一次访问时间的相关信息。

由于将来可能需要账户的创建时间来计算用户注册至今的时长，因此，也需要能够存储账户的初始时间，即使它可能用不到。

所以，本次的目标是：为user模型添加创建时间与上一次访问时间。

方案：
在用户模型中，首先存储获取到的基础时间戳信息。但是，用户模型里，有必要把它转换成人类可读的日期时间形式吗？
对这个问题的答案：
必须以原始的形式存储，直到需要把它展示给用户。

为了确保数据安全，不能再向以前那样直接改变用户模型。它永远只能通过UserDao进行赋值，在私有构造方法中实例化。
它将是只读对象。

代办事项：自定义异常，防止User模型（用户模型）用A != null的方式模糊判断。这是未来的操作，我目前还不会自定义异常，而且主要的更改目的不是这个，因此没有必要超前设计。
这样只会无谓的浪费我的时间，偏离原定的方向。


改造步骤：
首先，让用户模型能够读取、存储账户的创建时间与上一次的访问时间，这个模型才能够完整。
之后，修改登录逻辑，让用户登录成功后，对数据库中的last_accessed_time字段进行修改，让它变成最新登录时间的时间戳；

注册逻辑也要修改。它要在用户成功注册后，向数据库的create_time字段传输注册成功瞬间的时间戳。但是last_accessed_time不能改动，因为此时还没有进入登录流程。
我并未设计注册成功，即视为成功登录的简化流程。

登录流程的lats_accessed_time字段由应用层生成。将来，将由数据库直接管理。
注册流程的create_time字段给将在数据库里自动更改，任何应用层都不能直接接手它的操作。


关于如何改造的分析：
经统计，它有近20处调用。一旦发生变动，就有可能造成大规模代码的故障。
与User有关的调用信息如下：
[构造器部分]
不区分构造器类别，则一共被调用10次，还包括一个僵尸构造函数。

这里的重构已经顺利完工。
管理员视图的增加新用户功能涉及无参构造函数（一共调用了1次）。以下是详细说明。
√ ManageUserView.addUserView()实例化了一个user对象，作为返回值传递给MainController里的用户会话节点userSession()，用于向数据库里直接添加新的用户信息。
此时，涉及到UserDao操作。它最终传输给了UserDao.insertUser, 且没有数据库层冲突。

用户登录（管理员不参与）时，涉及到无参构造函数与User(User sourceUser)的调用。各调用一次。
UserAuthView.loginForm()也实例化了一个user对象，用于存储用户名和密码（它应该重构为DTO的登录请求），作为返回值，传送给UserAuthController.login()方法，
用于根据用户名，从数据库中获取对应的完整的用户信息，进行比较，从而判断出是否是这个人，并决定是否让用户登录，进入系统。
在传输过程中，用到了User(User sourceUser)构造函数。
为了保存来自数据库的完整的用户信息，我又实例化了一个userFromDB的User模型，负责存储根据UserDao.searchByUsername(User.getUsername())得到的完整用户信息。

UserDao.search**的方法里，多次涉及User模型的各种无参与有参构造函数的调用，出现频率很高。经统计，无参构造函数出现5次。
为了处理有多个结果集的用户信息查询，User模型还作为List<User> users出现了3次。（不是构造器）

这里的重构已经顺利完工。
√ User模型还被用来注册新用户（不被管理员操作）。它涉及这个构造函数：User(String username, String password, int role)，仅出现一次调用。
它与initPassword模型混用，进行这样的实例化：registeredUser = new User(init.getUserName(), init.getPassword_2(), init.getRole());
然后又被UserDao里的按用户名查找功能传递了完整的用户数据。由于我不确定用户是否输入了已经注册的用户名，它将有可能不完整，我还需要不断的验证信息。
但是数据库的传递不涉及构造函数。

它的构造器还被用来删除用户数据（deleteUserC(String)）。

已确认 User 模型的所有操作仅局限于用户模块。包含完整的 CRUD 操作。

已成功把User模型从注册场景分离。这一步能顺利实现，是因为它很容易从User模型的粘连中分开，而且创建时间的生成由数据库自动代劳了，所以它的重构很轻松就能完成。

疑问：本次重构的第二大步（登录场景）的目标是什么？第三大步是什么？（第一大步是刚刚完成的注册场景。）



目前计划的第三大步有以下选择：

我发现管理注册登录流程的控制器很混乱，即便加入了状态机技术，也起不了多大作用，因为主要的转换逻辑仍然由switch-case控制，几乎成为了switch-case地狱。
这是第一种选择，我希望登录流的控制器更好懂。
目前的用户会话管理，就负责登录后的流程：判断用户角色，进入对应的if-else分支。跳转到对应的首页，接收用户选择，然后用switch-case控制多达6种不同页面的跳转逻辑；管理员似乎少一点。
登录流程也类似，但是相对简单。首先告诉系统，现处于登录的流程（状态机）。登录流程里混杂了注册机制。用户在视图层选择登录或者注册，然后用switch-case跳转到对应的逻辑里，
完成操作后，把状态改变为“已登录”。

原计划第二步开始就考虑处理登录流程（注册流程已经单独实现，因为它最容易修改，也是用户生命周期的起点），但是发现似乎会牵扯到总控制器里的登录流，我因此感到迷茫。
但是，首要目标是解除与User粘连的代码块，让它易于重构。一旦涉及用户登录总控制器的改动，就十分容易混淆这两大步的界限。或者，就只能把这次重构压缩到两步以内。总之，十分难分辨。

或者，不再让User模型存储密码信息？





根据 GEMINI 2.5 PRO 的建议（https://g.co/gemini/share/aead9c964cbc），我最终采用蚕食策略。
即，逐步扩展新方法，然后慢慢地剥离老旧业务。

因此，改造计划如下：
一、扩展 User 模型。（已完成）
添加 createTime 和 lastAccessedTime 字段，添加只写访问器（Getter）。不修改构造器。
二、修改 UserDao 里的查找用户的系列方法。（已完成）
这个修改必须在新的方法上进行。在彻底迁移后，利用IDE的重命名功能，改回原名。
重点是扩展 ResultSet 字段。因为数据库已经变动，我们可以直接增加对应的时间字段，放入新增的 User 模型。
创建时间字段是数据库层的自动操作，你一定可以直接在模型里看到返回的数据。
三、最终实现以下目标：登录后，修改上次访问的时间。
同样扩展旧方法，设法让它能够修改上次访问的时间。
首先执行update语句（不能由触发器控制。因为只有在用户登录请求发送后，得到明确的、表示登录成功的结果时，才能修改这个字段）。
然后，才能存储结果集。顺序一定不能错。

这个改造计划的理由是：
一、扩展 User 模型（已完成）
仅为模型新增字段、功能，不涉及旧有方法的修改，这个操作是安全的，不会对已有内容造成冲突，可以开始处理。
二、修改 UserDao 里的查找用户的系列方法。（已完成）
1. 为了更有效的增加新功能，同时不与旧的项目产生冲突，我们将新的查询逻辑与旧的逻辑分开，就可以避免对旧的查询、读取方法造成影响。
这样，就可以逐步的扩展新方法，淘汰旧方法，能够在重构项目的同时，添加进新的功能。我们既能够整理旧有的代码，也不会影响新的需求的添加。
不断重复，直到所有现在不需要、未来也不需要的方法都消失了（可能并不会），就是本次大规模重构的成功；
2. 一旦未来的变动出现问题，我们可以轻易的回滚代码。
三、最终实现以下目标：登录后，修改上次访问的时间。
在 UserDao 中，创建新的 updateAccessTime 方法，以确保每个方法职责的唯一性。

完成上述操作后，目标达成，可继续按想法进行其他重构。
