我改变了用户的id规则，并且加入了账户创建时间与上一次访问的时间。经过代码检查，已确认不需要我做大幅重构，UserDao没有问题。
只需要小幅修改user模型，让它能够存储上一次访问时间的相关信息。

由于将来可能需要账户的创建时间来计算用户注册至今的时长，因此，也需要能够存储账户的初始时间，即使它可能用不到。

所以，本次的目标是：为user模型添加创建时间与上一次访问时间。

方案：
在用户模型中，首先存储获取到的基础时间戳信息。但是，用户模型里，有必要把它转换成人类可读的日期时间形式吗？
对这个问题的答案：
必须以原始的形式存储，直到需要把它展示给用户。

为了确保数据安全，不能再向以前那样直接改变用户模型。它永远只能通过UserDao进行赋值，在私有构造方法中实例化。
它将是只读对象。

代办事项：自定义异常，防止User模型（用户模型）用A != null的方式模糊判断。这是未来的操作，我目前还不会自定义异常，而且主要的更改目的不是这个，因此没有必要超前设计。
这样只会无谓的浪费我的时间，偏离原定的方向。


改造步骤：
首先，让用户模型能够读取、存储账户的创建时间与上一次的访问时间，这个模型才能够完整。
之后，修改登录逻辑，让用户登录成功后，对数据库中的last_accessed_time字段进行修改，让它变成最新登录时间的时间戳；

注册逻辑也要修改。它要在用户成功注册后，向数据库的create_time字段传输注册成功瞬间的时间戳。但是last_accessed_time不能改动，因为此时还没有进入登录流程。
我并未设计注册成功，即视为成功登录的简化流程。

登录流程的lats_accessed_time字段由应用层生成。将来，将由数据库直接管理。
注册流程的create_time字段给将在数据库里自动更改，任何应用层都不能直接接手它的操作。


关于如何改造的分析：
经统计，它有近20处调用。一旦发生变动，就有可能造成大规模代码的故障。

目前计划着手于注册逻辑的修改。
根据上面的调用逻辑，推到后面后发现，它最终涉及UserDao.insertUser(User user)。
它影响到管理员添加新用户和普通用户用不完整的注册请求信息添加新用户的声明。两个可能涉及不同的逻辑，似乎需要用到重载，比较麻烦。
这又是一个需要体检、诊断流程的地方，十分繁琐。

已确认insertUser涉及ManagerUserC.addUser和ManagerUserC.register两个方法，把这两个进行解耦就行。但是这不是简单的解耦。

register现计划采用数据传输对象（本场景下，用于软件与数据库之间的数据交换）的方式，向服务层（service）发送注册请求。
服务层验证了注册信息以后，向UserDao.insert传输有效的注册信息。最终由UserDao.insert把接收到的信息发送给数据库。它不做任何的验证操作。

然后，还要尝试解耦addUser的操作。ManagerUserC.addUser（这里是管理员对用户进行管理的地方）和UserAuthC.register（新用户注册）似乎采用了一样的验证逻辑，让人十分困惑。
这似乎是个二选一的操作。这两个似乎同样需要服务层介入。


以上就是我找到的问题所在（初步发现，问题还十分模糊）。
为了解决这个问题，还需要进一步体检，确认问题的复杂程度，找到需要修改、变换的地方。
现在必须设法用服务层解决业务逻辑。控制器层只负责指挥各个层级之间的交互。



最终的改造方案：
普通用户逻辑流程图：
普通用户发起请求 → DTO 接收 → 传递给服务层 → 服务层根据 DTO 生成不完整的User，传递给 UserDao → 普通用户注册成功。

管理员添加新用户的流程图：
用 ManageUserView.addUserView() 发起请求 → DTO 接受 → 传递给服务层 → 服务层根据 DTO 生成不完整的User，传递给 UserDao → 管理员成功添加新用户。


根据以上流程图的差异，需要重点注意的是以下的几个方面：
DTO 可以采用继承的关系，生成一个 NewUser 类的 DTO 私有基类，都含有用户名、输入的两次密码。
普通用户的注册请求的 DTO 直接继承 NewUser，无需任何修改，公开这个类，命名为 UserRegisterRequest.java
管理员用户继承 NewUser，然后增加角色信息。命名为AdminCreateUserRequest.java。
注意，两个dto在不同的文件夹分层下。

视图层的变动：只需要改变普通用户注册的视图，它们不能再输入角色信息了。这是唯一一个要改动的视图。

下一步，把控制器流程里的业务逻辑全部转移到服务层。
按核心业务领域与角色类别的方式分类。如，cn.edu.neusoft.service.user.UserAuthService.java，
这里的 UserAuthService.java 负责普通用户的登录、注册逻辑。
管理员和普通用户的注册应该有各自的逻辑，不建议抽象相似的部分，目的是让代码的灵活性、可定制性更大。
它只负责调度。我无需大幅修改注册的验证逻辑，只需要复制粘贴。

最后一步，简化dao层。它似乎已经够简洁了。
